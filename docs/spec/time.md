# Time: the clock, food and rest, the economy, the quest and the save file

Port rules for everything that changes over a quest rather than over a
frame: the day/time clock, hunger and sleep, buying and selling, quest
progression and the two endings, the attract-mode demo player, and the
save-slot format.

Data tables: `data/economy.json`, `data/quest.json`, `data/demo.json`,
`data/save.json`, all regenerated by `tools/spec_time.py`.
Item ids here are the 0-14 item classes shared with `player.md`.
Room ids are the numbers used in `world.md`.  Creature ids are the
per-creature state indices used in `creatures.md`.

Provenance is a trailing `[src: $XXXX]` tag; a port never needs it.

---

## 1. Frames, and what a "tick" is

Everything in this document is counted in **video frames**.  The game
drives one tick per raster interrupt; the spec's convention is **60
ticks/second (NTSC, 59.826 Hz)** -- see `docs/spec/README.md`.
[src: $8A9C, $A000]

The frame tick does three things in order: run the music, and then --
**only while the game loop is running** -- the clock, the creature
step, and (every `step_period` frames) one player state step.  "The game
loop is running" is false whenever a menu, a verb, a text prompt or a
wait-for-input is on screen, which is exactly the manual's promise that
the timer stops while the Option Menu is visible.  [src: $A015]

```
on_frame():
    music_tick()
    if not game_loop_running: return
    clock_tick()
    creature_step()
    step_counter += 1
    if step_counter == step_period:      # 8 walking, 6 leaping, 15 knocked down
        step_counter = 0
        player_state_step()
```

## 2. The clock

Two counters and nothing else.  `prescaler` free-runs over 256 frames;
each wrap costs one of the 35 `period` counts; when those run out, one
**time slot** has passed.  Neither counter is ever seeded to anything
but its natural value, so a port can hold them as plain integers.
[src: $B26F]

```
FRAMES_PER_WRAP   = 256
WRAPS_PER_SLOT    = 35            # 8960 frames = 149.8 s
SLOTS_PER_DAY     = 8             # one day = 19.97 min

clock_tick():
    if dream_state != 0: return           # the cloud world freezes time
    prescaler = (prescaler - 1) & 0xFF
    if prescaler != 0: return
    period -= 1
    if period != 0: return
    period = WRAPS_PER_SLOT
    advance_time()
```

`advance_time` is the only thing that ever moves the calendar, and three
other places call it directly: once per hour of sleeping in a nid, and
twice for eating wissenberries.  [src: $B109, $AC96, $B567]

```
advance_time():
    time_of_day += 1
    if time_of_day == 8:
        time_of_day = 0
        day += 1
    if day >= 51:                          # the only timeout in the game
        game_loop_running = False
        quest_time_up = True
        return                             # food, rest and spirit are skipped
    food -= 1
    if food < 0:
        food = 0
        if game_loop_running: collapse(OUT_OF_FOOD)
    rest -= 1
    if rest < 0:
        rest = 0
        if game_loop_running: collapse(OUT_OF_REST)
    spirit_energy = min(spirit_energy + 5, spirit_limit)
    period = WRAPS_PER_SLOT                # a forced hour re-phases the clock
```

`collapse` only sets a reason code and stops the game loop; the outer
loop acts on it (section 5).  The `game_loop_running` guard matters:
during REST and during a wissenberry the loop is already stopped, so
food and rest clamp at zero **silently** -- you cannot collapse in your
sleep.  The debt is paid the next time the clock or a ladder rung runs.

### Time of day

`time_of_day` is 0-7 and names the eight slots:

| slot | name | slot | name |
|---|---|---|---|
| 0 | EARLY MORNING | 4 | EARLY EVENING |
| 1 | LATE MORNING | 5 | LATE EVENING |
| 2 | EARLY AFTERNOON | 6 | MIDNIGHT |
| 3 | LATE AFTERNOON | 7 | LATE NIGHT |

Exactly two things read it: the status panel, and creature spawning --
an ambusher settles into a room for one time slot and reappears only
1 time in 4 outside it (see `creatures.md`).  **There is no day/night
cycle to draw**: no palette change, no charset change, no music change,
no lighting change.  Rooms below the root are dark at midnight and at
noon alike, and only a lamp or the spirit lamp lifts that.
[src: $983F, $B140, $8C6D]

### The day boundary

Rolling `time_of_day` past 7 increments `day` and nothing else.  Days
matter in four places:

- day 51 ends the quest (section 8);
- the final rank is computed from `day` (section 8);
- a gift-giving creature says COME BACK TOMORROW, MY FRIEND while the
  day it last spoke to you equals today, so a new day re-arms every
  gift-giver in the world;  [src: $3C83]
- the status panel prints it.

`day` is 1-based and starts at 1.

## 3. Food, rest and fatigue

Three drains, all of them decrements of the same two counters.

| drain | cost | when |
|-------|------|------|
| the clock | 1 food and 1 rest | every time slot |
| fatigue | 1 food and 1 rest | per 256 fatigue points spent |
| nothing else | | walking and falling are free |

Fatigue is a byte counter that starts at 255 when a quest starts and
only ever goes down, wrapping.  Each wrap is one food and one rest.
[src: $9F80, $975C]

```
FATIGUE_LADDER_RUNG = 1
FATIGUE_LEAP        = 5
FATIGUE_KNOCKDOWN   = 64

spend_fatigue(n):
    if dream_state != 0: return            # free in the cloud world
    borrowed = n > fatigue
    fatigue = (fatigue - n) & 0xFF
    if not borrowed: return
    food -= 1
    if food < 0:  food = 0;  if game_loop_running: collapse(OUT_OF_FOOD)
    rest -= 1
    if rest < 0:  rest = 0;  if game_loop_running: collapse(OUT_OF_REST)
```

So a lap of the counter is 256 ladder rungs, or 51 leaps, or 4
knock-downs.  Against the clock's one food per 150 s of play, climbing
is the cheap drain and crashing is the expensive one.

### Caps

`food` is capped at `food_cap - 1` and `rest` at `rest_cap - 1`, where
the caps start at stamina/2 + 1.  Both caps only ever move together (the
strange elixer moves them), so a port may keep one number, but the
original reads them from separate fields and the save file has both.
[src: $84D6, $ACA2, $B5D0]

### Restoring food and rest

| action | food | rest | cost |
|--------|------|------|------|
| EAT roast lapan / pan bread / fruit & nuts | +5 (capped) | -- | the item |
| EAT wissenberries | -- | -- | two time slots, 15 spirit energy |
| EAT a strange elixer | set to stamina/2 | set to stamina/2 | the item |
| HEAL | +2 (capped) | +2 (capped) | 5 spirit energy, spirit limit >= 15 |
| REST, per hour slept | -- | +4 (capped) | one time slot |
| return home (section 5) | refilled to the cap | refilled to the cap | one day |

The elixer also raises stamina by 5, raises both caps to stamina/2 + 1
and raises the carry limit by 5 -- the only permanent stat gain outside
spirit.  Roast lapan costs 15 spirit energy unless the character is Herd
or Charn (the two Erdlings), matching the manual's note that Kindar do
not get full benefit from it; the food bonus is the same either way.
[src: $B40C, $84B5]

## 4. REST, the nid, and the cloud world

REST needs to be indoors with the left half of a hanging nid one row
above the player, then one of three permissions:

1. the room is **room 9** -- the sky nid; this one also sets
   `dream_state = 1`;
2. the room is the character's own nid place;
3. someone offered you a nid this visit -- the room's creature has the
   "offers a nid" gift value and SPEAK has granted permission.

Otherwise: THERE IS NO NID HERE, or NO ONE OFFERED YOU A NID.
[src: $AC15]

```
rest():
    ...permission checks...
    walk right until the nid's right half is overhead, step back one
    switch to the lying-down sprite
    loop:
        draw_status_panel()
        wait for the stick to be centred
        ring the bell: 8 delays, chime-pause-silence-pause three times
        advance_time()
        rest = min(rest + 4, rest_cap - 1)
        run the host's REST event, unless that creature has been banished
```

Any joystick movement during one of the eight delays wakes you and ends
the verb -- the manual's "your character will not get up ... you must do
this".  Because each cycle calls `advance_time` while the game loop is
stopped, oversleeping drives food to zero silently.  [src: $AD13]

The host's REST event fires **every** hour of sleep, not once, and is
suppressed only by having banished that creature with the wand of Befal:

| host kind | effect |
|-----------|--------|
| token thief | every carried token is destroyed |
| shuba thief | every carried shuba is destroyed |
| Salaat trap | you wake in room 28, REST ends |
| Nekom trap | you wake in room 59, REST ends |

### `dream_state` -- the cloud world

A three-state flag: 0 normal, 1 "slept in the sky nid", 255 "in the
cloud world".  While it is non-zero the clock is frozen, fatigue is
free, and RENEW is refused.  [src: $C8, $B26F, $9F80, $A91A]

The exit is the **next door you walk through**, whichever door it is --
`dream_state` is tested before any lock check, so a locked door still
teleports:

```
on_door():
    if dream_state == 1:
        room = 190; player = (18, 14); indoors = False; dream_state = 255
    elif dream_state == 255:
        room = 9;   player = (24, 13); indoors = False; dream_state = 0
    else:
        normal door / gate handling
```

That is the walkthrough's Giver of the Spirit Bell: rest in the highest
Sky Grund nid, leave, and you are in the clouds; walk up to D'ol Neshom
in room 191, who blesses you (+5 spirit limit, a vision) and offers the
spirit bell -- the only one in the world, lying in that room; then enter
and leave the nid place again to come back.  [walkthru: "GIVER OF THE
SPIRIT BELL"; verified against rooms 9, 190, 191 and the object table]

The bell itself is a proximity alarm below the root: standing on a
doorway tile in an underground room while carrying it stops the loop and
prints THE SPIRIT BELL RINGS.  [src: $9FB3]

## 5. Collapse, RENEW and going home

One routine handles every "you lost a day" outcome.  There is no death,
no lives and no health bar.  [src: $A6FB]

```
return_home():
    room = nid_room; indoors = True; player = nid_position
    lie down
    day += 1
    spirit_energy = spirit_limit
    food = rest = food_cap - 1          # note: the FOOD cap is used for both
```

Five paths reach it, each with its own line of text:

| trigger | text |
|---------|------|
| food ran out | YOU SPENT A DAY RECOVERING FROM A LACK OF FOOD |
| rest ran out | YOU SPENT A DAY RECOVERING FROM A LACK OF REST |
| drowned | YOU WERE FOUND NEAR THE WATER.  TIME HAS PASSED. |
| RENEW | YOU WERE FOUND UNCONSCIOUS.  TIME HAS PASSED. |
| ambushed by a follower of D'ol Salaat | YOU WERE ATTACKED BY A FOLLOWER OF D'OL SALAAT.  TIME HAS PASSED. |
| ambushed by the Nekom | YOU WERE ATTACKED BY A MEMBER OF THE NEKOM.  TIME HAS PASSED. |

The two *kidnap* ambushes (and the two kidnap REST hosts) are different:
they move you to room 28 or room 59 and cost no day at all.

`return_home` does not check the day limit, so it can push `day` to 51
or past it; the timeout then fires at the next time slot rather than
immediately.

## 6. Economy

There is no price table and no money variable.  A **token is an ordinary
world object** of item class 8, and your purse is however many token
objects you are carrying.  [src: $4194, $4234, `data/economy.json`]

- Everything costs exactly **one token**, and everything sells for
  exactly **one token**, at every merchant.
- The world has 75 token object slots; 62 tokens are placed when a quest
  starts, so 13 slots are free.  A sale needs a free slot ("SORRY, I'M
  NOT INTERESTED" when there is none), and spending a token frees its
  slot.  That is the hard cap on how much money can exist.
- A token weighs 1; everything else weighs 5.
- Every character's own nid place starts with a shuba, one food item and
  three tokens on the floor.

BUY does not hand over goods.  It takes one token and grants *permission
to take* the merchant's one stock item; TAKE is what moves it.  Every
merchant stocks exactly one item class.

```
buy():
    if room creature is not a merchant: "THERE IS NO MERCHANT HERE"; return
    if not facing an adjacent merchant: "NO RESPONSE"; return
    if no carried token: "YOU NEED MORE TOKENS"; return
    if carried_weight + 4 >= carry_limit: "SORRY, YOU'RE CARRYING TOO MUCH"; return
    destroy one carried token (weight -= 1)
    take_permission = True
    "TAKE WHICHEVER ONE PLEASES YOU"

sell():
    ...same merchant and adjacency checks...
    item = cycle_inventory(only sellable classes)
    slot = first free slot in the token range
    if slot is None: "SORRY, I'M NOT INTERESTED"; return
    slot becomes a carried token; destroy the sold object
    carried_weight += 1 - weight(item)
    "HERE'S YOUR TOKEN"
```

Sellable item classes: honeylamp, roast lapan, pan bread, fruit & nuts,
shuba, trencher beak, wissenberries, vine rope.  The bell, the lamp, the
wand, tokens, the two keys and the elixer are not sellable.

The eight merchants, their rooms and their stock are in
`data/economy.json`.  Two other things destroy tokens: offering one to
the inner gate guard, and sleeping at a token thief's nid.

## 7. Quest state

Everything the quest remembers, beyond the object table and the player
stats, is in `data/quest.json` under `flags`.  The shape a port needs:

- **`quest_active`** -- a quest is in progress.  CONTINUE and SAVE both
  refuse while it is clear; both endings clear it.
- **`spirit_limit`** -- the master progress number.  It gates every
  spirit skill, and the six thresholds are 5 PENSE EMOTIONS, 10 PENSE
  MESSAGES, 15 HEAL, 20 GRUNSPREKE, 25 KINIPORT TOOLS, 30 KINIPORT YOUR
  BODY.  Five named creatures each add 5 on their first SPEAK; ten
  animals each add 1 on their first PENSE MESSAGES.  [src: $3DA9]
- **`vision_count`** 0-5 -- each spirit gain that still has a vision
  left prints the next one and bumps it.  The fifth animal counts as one
  such gain.  With five blessers *and* the animal milestone there are
  six triggers for five visions, so one of them shows nothing.
- **`pense_message_count`** 0-5 -- distinct animals pensed.
- **`wissenberries_offered`** -- offerings made to the outer gate guard;
  the second one sets the permanent gate flag.
- two **permanent gate flags**, stored as entries in the per-creature
  banished array.  The outer gate's flag is set by that second
  wissenberry offering.  No dialogue path sets the inner gate's flag; the
  only way to open that door for good is the wand of Befal on its guard
  (see `docs/spec/creatures.md`), else it costs a token on every visit.
- **`falla_key_revealed`** -- speaking to D'ol Falla; without it TAKE
  refuses her key.
- **`dream_state`**, **`lamp_index`/`lamp_fuel`**, **`fatigue`**,
  **`quest_time_up`**, **`spirit_bell_rang`** as described above.
- the two **per-creature arrays**, 128 entries each, indexed by creature
  id: *banished* (bit 7, set by the wand of Befal) and *day stamp* (bits
  0-6 = the day last spoken to, bit 7 = its once-per-quest spirit gift
  is spent; for ambushers bits 0-4 instead hold the time slot they
  settled in).

Two per-visit flags are **not** quest state and must be cleared on every
room load: the take permission granted by SPEAK or BUY, and the door
permission granted by a gate offering.

### Ordered milestones

`data/quest.json` carries the fourteen walkthrough milestones with, for
each, the walkthrough section it comes from and the code fact that
confirms it.  The spine is: pick up your starting kit; buy a trencher
beak and reach the Hermit; reach the Child in the Garden; take a vine
rope to the sky nid and sleep there for the cloud world and the spirit
bell; buy berries, a token and lamps and get below the root for Vatar;
pense five animals; get the two temple keys and the spirit lamp; raise
the spirit limit to 30; and offer Raamo a shuba.

## 8. The two endings

**Winning.**  OFFER a shuba or a vine rope to the creature whose state
index is `$49` -- Raamo, who exists in exactly one room in the world
(room 464).  Any other item to him gets THAT WON'T HELP; the same offer
to anyone else gets NO RESPONSE.  [src: $43CC, $449C]

```
quest_complete():
    "I AM RAAMO, THE SPIRIT GIFTED."
    "YOU HAVE SAVED MY LIFE AND FULFILLED THE PROPHESY.
     THE QUEST IS COMPLETE.  GREEN-SKY IS SAVED."
    play tune 0, wait for it to finish
    "YOU HAVE FINISHED THE QUEST IN <day> DAYS. YOU ARE A"
    rank = "MASTER QUESTER."          if day < 15
           "HIGHLY GIFTED QUESTER."   if 15 <= day < 30
           "GIFTED QUESTER."          if day >= 30
    play tune 2, wait for it, wait for a trigger press
    quest_active = False
    -> main menu
```

That is the entire score: the day count and a rank derived from it.
Nothing else about the run is reported and nothing is written to disk.

**Running out of time.**  `advance_time` reaching day 51 stops the loop
and sets the timeout flag; the outer loop prints THE LIGHT FADES INTO
DARKNESS... / THE TIME FOR YOUR QUEST HAS ENDED. / GREEN-SKY AWAITS THE
RISE OF ANOTHER QUESTER., plays tune 0, waits for a trigger, clears
`quest_active` and returns to the main menu.  Fifty complete days, as
the manual says.  [src: $8E76]

Neither ending saves.  Nothing in the game ever saves automatically.

## 9. The attract demo

The demo replaces the joystick read with a byte script.  One script
entry can cover many reads, and a "step" is one input read by the player
state machine -- i.e. one state step, every `step_period` frames.
[src: $3000, `data/demo.json`]

```
demo_input():
    if the real fire button is down:          # the only way to interrupt
        game_loop_running = False; request_menu(); return IDLE
    steps -= 1
    if steps != 0: return held_value
    return decode_next_opcode()
```

The returned byte is shaped like the joystick port -- bit 0 up, 1 down,
2 left, 3 right, 4 fire, all active low, idle = `$1F`.  Bits 5-7 are
never tested as input, which is what leaves the high bytes free to be
opcodes.

| byte | operand | op | effect |
|------|---------|----|--------|
| `$00`-`$7F` | -- | `tap` | this value for one step |
| `$80`-`$BF`, `$C6`-`$FE` | count | `hold` | this value for `count` steps |
| `$C0` | tune | `music` | start the tune, then decode the next opcode at once |
| `$C1` | -- | `delay` | one busy-wait of about 2/3 s, then one idle step |
| `$C2` | n | `delay` | n such waits, then one idle step |
| `$C3` | room | `goto_room` | end the script and hand the room to the outer loop |
| `$C4` | page | `text_page` | print an intro text page, then one idle step |
| `$C5` | -- | `end_rest_delay` | end the running REST bell delay, then one idle step |
| `$FF` | -- | `end_demo` | clear the demo flag; neither script uses it |

Two scripts ship: the **intro** (151 bytes, room 157, indoors, ends by
handing over room 228) and the **quest** (523 bytes, room 228, outdoors,
ends by handing over room 157).  The intro interleaves movement with the
four text pages; the quest script is pure gameplay -- it walks, climbs,
opens the tool menu with down+fire, picks cells, and rests in a nid.

Flow: on a cold boot the intro script runs once and the game drops into
the main menu.  From SAMPLE QUEST the two scripts chase each other's
`goto_room` forever until the fire button is pressed.  The keyboard is
never polled.  [src: $952B, $93C0]

While the demo runs, the player is character slot 5, a shuba is put
straight into the inventory, and TAKE skips its "IT WAS NOT OFFERED TO
YOU" check so the scripted pickups always work.  [src: $9C6E, $AD6D]

### `end_rest_delay`, and why it is not dead

`$C5` writes 1 into the two bytes the REST bell delay uses as its
counters.  That delay is a loop that calls the input routine once per
iteration and would otherwise run 256 x 21 times per chime -- far more
input reads than the whole script has bytes.  Setting both counters to 1
makes the delay finish on its very next iteration.

The proof is arithmetic: one full pass of the REST loop makes exactly
**eight** calls to that delay (two before the bell, then two per chime
for three chimes), and the quest script contains exactly **eight**
`C1 C5` pairs, immediately after the menu navigation that selects the
REST cell (down+fire to open the menu, right, right, down, down, down,
fire -- column 2, row 3 of the 5x4 grid, which is REST).  `C1` supplies
the visible pause, `C5` releases the delay.  The eight pairs are
followed by an `up` tap, which is what wakes the sleeper.
So `$C5` is a demo-only "let the current REST chime finish" opcode.
Confirmed in VICE: entering SAMPLE QUEST and polling the text screen
shows the tool menu, then the status panel -- which only REST and STATUS
draw, and the script never selects STATUS -- with the player asleep in
room 330.
[src: $30A1, $AD13, $ACE7, script bytes `$32D6`-`$32FB`]

A port that reimplements the demo can drop the opcode entirely if its own
REST delay is not a spin loop; it needs it only to reproduce the
original's pacing.

## 10. Save and load

A save is an ordinary PRG file on a separate storage disk, five slots
named `QUEST1`..`QUEST5`.  The payload is a flat 1408-byte image; with
the two-byte load-address header the file is 1410 bytes.  Full field
list in `data/save.json`.  [src: $3968, $39C6]

| offset | size | what |
|--------|------|------|
| 0 | 2 | load address, little endian, always `$2000` |
| 2 | 256 | per object: the low byte of its room |
| 258 | 256 | per object: its screen column |
| 514 | 256 | per object: bits 0-4 row, bit 5 carried, bit 6 exists, bit 7 room high bit |
| 770 | 128 | per creature id: banished flag (and the two permanent gate flags) |
| 898 | 128 | per creature id: day stamp / gift-spent bit |
| 1026 | 256 | the variable page (day, time of day, all six stats, both caps, carry limit, home nid, clock counters, carried weight, player position) |
| 1282 | 128 | the zero-page block (current room, character, quest flags, fatigue, lamp, dream state, vision and pense counters) |

The two 256-byte blocks are copies of live pages, so most of their bytes
are per-frame scratch; the fields worth reading and writing are
enumerated in `data/save.json`.  An object entry whose flags byte is 0
is a free slot.

```
save():
    current_room = saved_room          # the room the player was in when the
                                       # main menu was entered
    write the object table, the creature arrays, the variable page and the
    zero-page block as one 1408-byte image
```

```
load():
    remember which character's sprite file is currently in memory
    read the image back over the four regions
    restore that sprite-file id, discarding the saved one
    -> main menu; CONTINUE reloads the character's sprites if it differs
```

Not in the file: the world itself (room blocks are re-read from the data
disk), the character sprite file (reloaded by name), and any score.

A port that wants to read real C64 saves needs only the offsets above;
one that wants to *write* them must also scratch the old file first, as
the original does, because the drive will not overwrite in place.

## GAPs

- **GAP:** the clock rate (256-frame prescaler x 35 x 8 slots) is read
  off the code, not measured on hardware.  Nobody has timed a real day
  against a stopwatch, and the raster interrupt could in principle be
  missed under disk I/O.
- **GAP:** the walkthrough lists four blessers plus the animals as the
  five vision sources, but the code has five blessers (it also counts
  Raamo's Mother).  With the animal milestone that is six triggers for
  five visions, so at least one gain shows no vision.  Which one depends
  on play order; no ordering is enforced.
- **GAP:** the ambush handler has no case for Raamo's creature kind, so
  if Raamo could ever walk into the player's cell the game would print
  the Nekom attack message.  Whether his patrol can actually reach the
  player has not been checked.
- **GAP:** two of the four ambush effects (the kidnaps to rooms 28 and
  59) have not been observed in the running game, only read.
- **GAP:** `return_home` can push the day past 51 without the timeout
  firing until the next time slot.  Not verified in play.
